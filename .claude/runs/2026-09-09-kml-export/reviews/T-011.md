## Ranked residual risks (for the user)

1. **No real KML-viewer verification was ever possible in this environment** (any phase). Structural validity is proven; visual correctness in Google Earth/QGIS is not. Recommend the user open one real export once, at their convenience.
2. **Trip export is uncapped in size while the set endpoint is capped at 100** (design §2.3/§1.4) — today's largest trip (45 flights, 1.67 MB) is fine, but a much larger future trip has no ceiling, unlike the set endpoint's 100-id cap.
3. **5,000-point decimation (`MAX_TRACK_POINTS`) has never been exercised against a real flight** — the live DB's longest flight is 2,242 points (design §0/T-006 review), so the decimation branch is covered only by unit tests with synthetic data, not a live fixture.
4. **README doesn't mention the `gx:Track`/animated-playback option** design §9.2 flagged as a clean, additive follow-up if the user later wants Google Earth's fly-along view — not a defect, just an unlisted future option worth surfacing.
5. **Planned-route overlay (`.lnmpln` legs) is not exported**, only the flown track (design §1.2/§9.2) — intentional scope cut, worth the user knowing if they expected planned+flown together.
6. POST for a read-only export (set endpoint) is not pasteable as a URL — accepted trade-off in design §2.3, not a defect.
