# T-003 — Sidebar component + AppShell wiring

## Changes

- `client/src/components/Sidebar.tsx` (new) — fetches `/api/trips` and
  `/api/flights` via `apiFetch` (Home.tsx's Promise.allSettled pattern, failing
  soft: renders whatever loaded, shows a one-line `.sidebar-error` message on
  any failure). Refetches on mount, on `location.pathname` change, on a 30s
  interval, and on `visibilitychange`. Renders `<nav className="sidebar">` →
  Home NavLink, Trips section (disclosure + `NavLink to="/trip/:id"` with
  Active badge + leg count, expandable sub-items `Leg {n} · DEP → ARR` /
  aircraft fallback), Flights section (Home.tsx:161-163's `tripFlightIds`
  logic verbatim). Auto-expand seeds from the route (`/trip/:id` or the trip
  holding `/flight/:id`) via a `useRef` set of user-toggled trip ids that wins
  over the route seed once touched. `.sidebar-toggle` collapses the rail,
  persisted to `localStorage['sidebarCollapsed']` (`'1'`/absent), defaulting
  to collapsed at `window.innerWidth <= 900`.
- `client/src/App.tsx` — `AppShell` now renders
  `<Header/><div class="app-body"><Sidebar/><div class="app-main"><Routes>…</Routes></div></div>`.
  The `export function App()` route table (`/device`, `/override`, both
  `/print/*` routes, and the comment) is untouched — see diff below.
- `client/src/index.css` — appended `.app-body`/`.app-main` flex rules and the
  full `.sidebar*` block, plus a `@media (max-width: 900px)` rule that takes
  an expanded rail out of flow (`position: fixed`) so it overlays rather than
  squeezes `.app-main` at narrow widths.
- `.claude/runs/2026-09-09-sidebar-nav-legs-paging/reports/seed-sidebar-fixture.mjs`
  — adds a second, non-active trip (2 flights) and 3 standalone flights to a
  **scratch** `flights.db` copy (refuses the live path, same guard as T-001's
  `seed-many-legs.mjs`).
- `.claude/runs/2026-09-09-sidebar-nav-legs-paging/reports/verify-sidebar.mjs`
  — the puppeteer checker for the DOM criteria (placed under `reports/`, not
  `tools/`, for the same ESM-resolution reason T-001's `verify-pagination.mjs`
  gives).
- `.claude/runs/2026-09-09-sidebar-nav-legs-paging/reports/T-003-verify-output.txt`
  — full 30/30 transcript from the final build.

## Risks

- `git status --porcelain` includes `2026-09-07-gpx-import/` and
  `2026-09-08-docker-pdf-export/`, untracked run directories that predate
  this task and are outside `allowed_paths` — not created or touched here,
  same situation T-001's report flagged.
- `client/src/pages/TripDetail.tsx` and part of `client/src/index.css` carry
  T-001/T-002's diff, still uncommitted in the working tree ("merged and
  approved" evidently means workflow-approved, not git-committed). I diffed
  it against T-001's own report to confirm it's unchanged by me, but I did
  not re-verify T-001's acceptance criteria myself — that phase's own review
  already covers it.
- The sticky offset (`top: 61px` in `.sidebar`/`.sidebar-toggle`) is a
  measured constant, not computed from the header's actual rendered height —
  if `.header`'s padding/content ever changes, this will need a matching
  update. No acceptance criterion tests the sticky offset directly; I
  measured it empirically (`#map` bounding box, no overlap observed) but
  didn't add a scroll-based regression check for it.
- The `@media (max-width: 900px)` rule (expanded rail becomes `position:
  fixed`, overlaying instead of squeezing) is my own reasonable-design choice
  to satisfy "a `@media (max-width: 900px)` rule" — the task names the
  breakpoint (matching the existing `.live-grid` one and the JS collapse
  default) but not the exact rule content, so this is unverified against any
  specific acceptance criterion beyond "no horizontal overflow" (which was
  checked, but only at 1280px, not below 900px).
- Standalone-flight label format (no "Leg N" prefix, just route-or-aircraft)
  is my own reasonable reading — the spec gives the exact label format for a
  trip's sub-items but not for the ungrouped-flights section.
- `is-active` styling reuses `.sidebar-item`'s own background/color rather
  than any pre-existing color token, since no CSS variables exist in this
  file to reuse (per the constraint, none were added).
