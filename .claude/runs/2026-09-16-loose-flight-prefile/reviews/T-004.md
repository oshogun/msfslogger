### 2. End-to-end, re-derived on a scratch server

Setup: `npx tsc --outDir <scratch>/dist`, `node dist/index.js` with
`PORT=3117 BIND_HOST=127.0.0.1 FLIGHTS_DB_PATH=<scratch>/db/flights.db`
(a copy of `flights.db` + `-wal`/`-shm`), `SIMBRIEF_API_BASE_URL` pointed at a
local stub serving `samples/simbrief/simbrief.userid.json`. Session via a
scratch-only operator password; read routes via `x-ingest-token`.

- **Loose leg created** — `POST /api/planned-legs/simbrief` → `HTTP 201`,
  `{"id":35,"trip_id":null,"seq":1,…,"destination_ident":"UHSS"}`.
- **Dispatch release (independent check)** —
  `GET /api/planned-legs/35/acars-messages` → `HTTP 200`, one message:
  `uplink dispatch | DISPATCH RELEASE | dedup=dispatch:leg:35 | payload=yes`,
  body `DISPATCH RELEASE / FLT SHG037 / UHPP UHSS ALTN NONE / ACFT BE20 N201SB / CRZ FL280`.
- **Loadsheet** — `POST …/35/acars-messages/loadsheet` → `HTTP 201`,
  `created true`, `block_fuel 1241, payload 642, zero_fuel_weight 4511`; repeat
  call → `HTTP 200, created=false` (dedup intact).
- **WX** — `POST …/35/acars-messages/wx {"icao":"UHSS"}` → `HTTP 201`, real
  `METAR UHSS 161700Z …` reply filed against `planned_leg_id: 35`.
- **Ground session on the loose leg** — `POST /api/ground-sessions
  {"icao":"UHPP","planned_leg_id":35}` → `GET /api/status`:
  `{"plannedLegId":35,"tripId":null,"tripName":null,"departureIdent":"UHPP","destinationIdent":"UHSS"}`
  — the `buildGroundSessionCache` guard (§6.2) in production, no throw.
- **Live status while flying, linked by hand** — flight 95 started near UHPP,
  `PUT /api/flights/95/planned-leg {"plannedLegId":35}` → 200, then
  `GET /api/status`:
  `{"plannedLegId":35,"tripId":null,"tripName":null,"destinationIdent":"UHSS","nextWaypointIdent":"LEDRU","remainingDistanceNm":658.9,"distanceIsApproximate":true}`
  — matches design §6.3 field-for-field.
- **OOOI events (independent check)** — flight 95's thread after rollout:
  `OUT / OFF / ON / IN`, dedup `oooi:flight:95:<EVENT>`. `ON` and `IN` bodies
  read `ACFT BE20 DEST UHSS` and `ON`'s payload is
  `{"v":1,"event":"ON",…,"airport_icao":"UHSS","estimated":false,"planned_leg_id":35}`
  — the loose leg reached the OOOI payload. `OUT`/`OFF` carry no leg because
  they are filed at `startFlight()`, before the manual link; that is existing
  behaviour, not a loose-leg effect.
- **No auto-match of a loose leg, with a trip actually active** — trip 1
  (`is_active=1`) was active throughout; flight 95 departed UHPP, the loose
  leg's own departure, and `GET /api/status` had **no** `plannedLeg` key until
  the manual `PUT`. The candidate join returned only trip legs
  (`[4,5,6,…,32]`, never 35). Confirms §6.4 / must-not-change 10.

Failure paths: thread on leg 9999 → `404 PLANNED_LEG_NOT_FOUND`; loadsheet on a

## Findings

**Non-blocking — `src/flightManager.ts:142`, `?? ''` fallback kept against the
freeze.** Design § 6.2 states: "`buildPlannedLegCache` today writes
`tripName: getTripName(leg.trip_id) ?? ''`. The `?? ''` fallback goes away".
The implementation is
`tripName: leg.trip_id !== null ? getTripName(leg.trip_id) ?? '' : null`.
Not blocking: the branch is unreachable (the foreign key makes a missing trip
impossible — the design says so itself), the declared type is unchanged, and
T-004's own criterion ("calls `getTripName` only when `leg.trip_id !== null`
and sets `tripName: null` otherwise") is satisfied. Drop the `?? ''` when the
file is next touched.
