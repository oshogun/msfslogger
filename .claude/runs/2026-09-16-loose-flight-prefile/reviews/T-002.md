## Migration — scratch copy of the live database

`cp flights.db flights.db-wal flights.db-shm $SCRATCH/`, then `applySchema()`
from a scratch-compiled build under Node 20.20.2:

```
COPY before trip_id: {"type":"INTEGER","notnull":1}
COPY before counts: {"flights":56,"trips":1,"planned_legs":22,"waypoints":188,"alternates":7,
                     "acars_leg":2,"gs_leg":4,"flights_leg":21,"seq":34,"digest":"len=1725"}
MIGRATION run 1 ms: 11
COPY after  trip_id: {"type":"INTEGER","notnull":0}
COPY after  counts:  (identical to the line above)
DIGEST identical: true          COUNTS identical: true
fk pragma restored: 1           integrity_check: ok      foreign_key_check rows: 0
indexes: idx_planned_legs_source(trip_id, source_sha256), idx_planned_legs_trip(trip_id, seq)
child REFERENCES: flights/ground_sessions → ON DELETE SET NULL; planned_waypoints/planned_alternates/acars_messages → ON DELETE CASCADE
after 3 runs trip_id: {"notnull":0}   after 3 runs counts identical: true digest identical: true
```

The digest is `group_concat(id||trip_id||seq||status||source_sha256)` over all
22 legs ordered by id — lossless, not just equal in count. `sqlite_sequence.seq`
stayed `34` while `MAX(id)` is `33`, so the AUTOINCREMENT counter was carried
across the rebuild (the one thing a naive rebuild loses). Runs 2 and 3 were
no-ops. On a **fresh** scratch database: `FRESH trip_id: {"notnull":0}`,
`FRESH fk pragma after applySchema: 1`, and a `trip_id NULL` insert was accepted.

The dangerous part of §3.3 is implemented as frozen: the `foreign_keys` pragma
is toggled **outside** any transaction, re-read and thrown on if it did not
take, the rebuild uses raw `BEGIN`/`COMMIT` rather than `db.transaction()`,
drop-then-rename (never rename-out-of-the-way), explicit 50-column lists on
both sides of the `INSERT … SELECT`, `foreign_key_check` before `COMMIT`, and
the prior pragma value restored in a `finally`. Call site is the last
`planned_legs` statement in `applySchema`, with the ordering constraint stated
in the comment.
