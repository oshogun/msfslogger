## AC3 — CSRF is not loosened for a cookie-bearing request

```
### cookie + MISMATCHED Origin, POST /api/flights/92/acars-messages
HTTP/1.1 403 Forbidden
body: {"error":"Cross-origin request rejected"}

### cookie + valid token + MISMATCHED Origin   -> {"error":"Cross-origin request rejected"} [HTTP 403]
### stale/forged cookie + valid token + hostile Origin -> {"error":"Cross-origin request rejected"} [HTTP 403]
### cookie + MATCHING Origin                   -> 201  (browser flow unchanged)
### token-only + hostile Origin, no cookie     -> 201  (design § 7.2 step 3b)
### WRONG token + hostile Origin, no cookie    -> {"error":"Cross-origin request rejected"} [HTTP 403]  (§ 7.3 precedence)
### off-list POST /api/ground-sessions, cookie + hostile Origin -> 403 (unchanged)
```

A token cannot rescue a cookie-bearing request from the Origin check, which is the
precondition the whole exemption rests on. **Pass.**

## Findings — non-blocking

1. **`npm run build` was run in the live checkout, not a scratch copy.** `dist/auth/
   ingestScope.js` is dated 12:30:28 and `client/dist/index.html` 12:30:25, both before my
   review started at 12:37. ENVIRONMENT.md § "Verifying a client-side change" and the
   2026-09-15 lesson both say to build in a scratch root. No damage found: the tree is
   shippable, `tsc` is clean, and `client/dist` was rebuilt from unmodified committed
   source. But the Orchestrator should know that live `dist/` already contains this run's
   code, so the user's next restart picks it up whether or not the commit lands.
2. **`npm run dev:server` does not start — pre-existing, not this run.** `npx ts-node
   src/index.ts` fails with `src/auth/middleware.ts(19,34): error TS2339: Property 'user'
   does not exist on type 'Session & Partial<SessionData>'`. I reproduced the identical
   error at line 13 on a pristine `git archive HEAD` checkout, so it predates T-002:
   `src/auth/express-session.d.ts` is reachable via tsconfig `include` but not via
   ts-node's import graph. Worth its own tier-1 fix (`ts-node --files`, or import the
   augmentation), out of scope here.
3. **design § 8's grep claim is imprecise.** It says `grep -rn "timingSafeEqual" src/`
   returns exactly one file; it returns two — `src/auth/password.ts:60` uses it for the
   password comparison. The property that matters (one ingest-token comparison, one home)
   does hold. Design wording, not code.
4. **`tests/ingestScope.test.ts:340`** — the comment "Every route this run's design put on
   the list" gestures at a document the next reader of `tests/` cannot locate. The
   surrounding code already says "the finalized list"; prefer that.
5. **`HEAD` on a scoped route 401s under the token** while a session `HEAD /api/status`
   gets 200, since express maps HEAD to the GET handler but the allowlist matches method
   `GET` only. This is frozen behaviour (design § 14.2 lists HEAD as `false`), so it is
   conformant — but if the MCDU client uses `HEAD` as a liveness probe it will read that
   401 as "not authorized". Worth one line in the client hand-off.
