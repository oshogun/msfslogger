## A real finding, not just a test artifact

While writing the §6.4 "restoreMocks trap" self-test I found the design's premise for it is
factually wrong for this shape of mock. I verified against
`node_modules/@vitest/spy/dist/index.js` (vitest 4.1.11, the installed version): `vi.fn()`
mocks are tracked in a `REGISTERED_MOCKS` set, but `vi.restoreAllMocks()` — what
`vitest.config.ts`'s `restoreMocks: true` runs before every test (confirmed in
`node_modules/vitest/dist/chunks/test.DNmyFkvJ.js`, `clearModuleMocks()`) — only iterates a
separate `MOCK_RESTORE` set populated exclusively by `vi.spyOn()`. A plain `vi.fn()` (which is
what `dbMock`/`airportsMock` are, per §6.1's "plain objects of vi.fn()s") is completely untouched
by `restoreMocks: true`: neither its installed implementation nor its call history is cleared
between tests. I reproduced this directly (`tests/_probe.test.ts`, deleted after use) before
fixing the module.

Practical effect on this module, already fixed here: `resetMocks()` is not defending against
`vi.fn()` implementations being silently stripped (they aren't) — it is the *only* thing that
resets `dbMock`/`airportsMock` between tests at all, for both implementation and call history. I
implemented each default install with `.mockReset().mockImplementation(default)` rather than bare
`.mockImplementation(default)`, since the latter never clears prior call history — a test in
T-004/T-005/T-006/T-008 that didn't call `resetMocks()` in `beforeEach` would otherwise see
`.mock.calls` accumulate across tests and get false-positive/false-negative
`toHaveBeenCalledWith` results. The self-test's two §6.4 tests now assert the verified real
behavior: `vi.restoreAllMocks()` leaves a manual override in place (the actual trap), and
`resetMocks()` is what a consuming test must call to get a clean mock.

This doesn't require touching `vitest.config.ts` (T-001's, outside my `allowed_paths` and
correct as far as it goes — `restoreMocks: true` is harmless, just not doing what §6.4 describes
for plain `vi.fn()`s). It matters for whoever writes T-004/T-005/T-006/T-008: they must call
`resetMocks()` explicitly in a `beforeEach`/`afterEach`, not rely on vitest's config to clean
`dbMock`/`airportsMock` for them.

## Risks / assumptions
- Named real positions (§4.7) are exported as `{ lat, lon }` objects (`KSBA = { lat: 34.426201,
  lon: -119.841507 }`, etc.) since the design shows bare coordinate pairs but `northOfNm(pos, nm)`
  needs a `{lat, lon}` shape and the design doesn't spell out the constant's own type. If a
  consuming task expected separate `KSBA_LAT`/`KSBA_LON` scalars instead, that's a one-line
  change at the export site — no consumer exists yet to break.
- `refusalFor()` in `src/legMatcher.ts` is not exported, so criterion 3's "eligible by refusalFor()"
  is asserted by checking the exact fields it reads (`status`, `linkedFlightId`,
  `departureIsAirport`) rather than by invoking it — flagged in both this report and a test
  comment.
- Did not touch `vitest.config.ts` per `allowed_paths`; the `restoreMocks: true` vs. plain
  `vi.fn()` mismatch above is worth the Orchestrator/Designer knowing about even though no code
  change is needed on my end.
