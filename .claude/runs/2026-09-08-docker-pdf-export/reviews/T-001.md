## End-to-end verification (beyond the listed criteria, addressing the
implementer's own flagged risk)

The report's risk list (only part of the report read, per instructions)
flagged: "If Puppeteer's own sandbox flags... aren't already compatible with
a non-root Alpine Chromium launch, first real export attempt in the container
could still fail." I tested this directly rather than taking it on faith:

- Started the scratch image as a container (`msfslogger-review-container`,
  port 3100, **not** 3000) with a copied `flights.db`/`-wal`/`-shm` (never the
  live files) bind-mounted read-write into a scratch dir.
- Container logs on boot: `[DB] Database ready`, `[HTTP] Server running at
  http://localhost:3000` (in-container) — clean start.
- `curl http://localhost:3100/api/flights/60/export.pdf` → `HTTP/1.1 200 OK`,
  `Content-Type: application/pdf`, 114301 bytes. `file` confirmed: `PDF
  document, version 1.4, 1 page(s)`.
- Container logs during the request: `[PDF] Launching headless browser...`,
  `[PDF] Rendering http://127.0.0.1:3000/print/flight/60` — no errors, no
  sandbox crash.

This resolves the flagged risk: Chromium launches and renders successfully
under the container's default (root, since no `USER` directive is set)
process, with the existing `--no-sandbox`-style flags in `pdfExport.ts`
(unmodified, out of scope) working as-is against Alpine's native build.

## Design conformance

Compared against `intake.md`'s frozen decision (verbatim README snippet:
`apk add chromium nss freetype harfbuzz ca-certificates ttf-freefont
font-noto` + the two `ENV` vars + `init: true`). The implementation matches
the frozen snippet exactly, applied only to the `production` stage (plus the
`server-builder`-only `PUPPETEER_SKIP_CHROMIUM_DOWNLOAD` addition, which
`intake.md` explicitly scopes in as "same seam, not a separate task"). No
deviation, no Debian-base switch (correctly avoided per the frozen decision).
