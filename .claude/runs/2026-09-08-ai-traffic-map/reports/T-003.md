## Risks / unverified

- The inspector's Section D (auth, kill switch, connected-flag rows S29–S33)
  spins up a real, ephemeral, loopback-only express app with
  `createIngestRouter` rather than importing `src/server.ts`/`createServer()`
  directly — done deliberately to avoid pulling in `src/db.ts` (which, while
  it doesn't open `flights.db` at import time, is safer not to import at all
  from a CLI that must never touch the live database). This means the
  inspector never exercises the real `express.static`/SPA-catch-all stack;
  S36 is checked structurally instead (source-text ordering), as noted in
  criterion 2.
- Node's native `fetch` (undici) held a keep-alive client handle open even
  after every ephemeral server in Section D was closed with
  `closeAllConnections()`, which kept the CLI process alive past `main()`
  finishing. Worked around with an explicit `process.exit()` at the end of
  `main()` — a normal pattern for CLI scripts, but worth knowing if this file
  is ever extended and expected to `await` something after `runHttpRows()`.
- I did not add a `TRAFFIC_ENABLED=0` end-to-end curl transcript against the
  scratch server (S31/S32's HTTP behaviour) beyond the inspector's Section D
  coverage — the task's acceptance criteria didn't explicitly ask for it as a
  separate curl transcript, and it's covered by the inspector's real
  HTTP-level test against `createIngestRouter`. Flagging in case the Reviewer
  wants a literal curl transcript too.
- `client/dist` and `airports.json` were copied into each scratch directory
  so the scratch server's static/airport-lookup paths resolved the same as
  production; neither is part of this task's `allowed_paths` and neither was
  modified, only read.
