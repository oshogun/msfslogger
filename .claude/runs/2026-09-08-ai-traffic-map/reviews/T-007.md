## Non-blocking follow-ups

1. **`agent/agent.js:97-105` — `decodeTrafficRecord` has no `try`/`catch`.** A
   buffer shorter than 44 bytes would make `readFloat64` throw *synchronously
   inside the SimConnect listener*, which is an uncaught exception that kills
   the agent and with it the user's flight logging. I could not construct an
   input that reaches it (the six registrations at `:139-144` fix the layout and
   match the six reads exactly), and the pre-existing `simObjectData` handler
   `:168-177` has had identical exposure since day one — so this is hardening,
   not a regression. Wrapping the `simObjectDataByType` body in a
   `try/catch` that logs and drops the sweep would make the traffic path
   strictly safer than the frame path it rides beside.
2. **`agent/agent.js:252-253` — a question, not a finding.** `handleDisconnect`
   is bound to both `'quit'` and `'close'` (pre-existing, unchanged by this
   run). If `node-simconnect` emits both for one disconnect, `tryConnect` is
   scheduled twice and two handles result. I cannot reproduce this without a
   sim. Traffic's exposure is bounded: two interleaved sweeps would merge in the
   module-level `sweepBuffer` but `buildTrafficBatch` de-dupes by id
   (`traffic.js:86-89`), so the worst case is a schema-valid batch mixing two
   sweeps — no corruption of the frame path.
3. **`client/src/components/LiveMap.tsx:16-18`** — the comment says "no
   drop-shadow depth cue", but the icon does carry a (lighter) drop-shadow, per
   frozen §7.2. Comment nit; the code is correct.
4. **Malformed JSON to `/api/ingest/traffic` returns express's default `400`
   HTML page with a full stack trace including absolute `node_modules` paths.**
   Identical on the pre-existing `/api/ingest/frame` (verified), so pre-existing
   and out of this run's scope — but an ingest-router error handler would stop
   leaking paths on all three routes at once.
5. **§3.4 wording vs `agent.js:197-199`.** Guard 2 uses whatever `userLat`/
   `userLon` the *latest* frame set, not strictly "the frame that triggered the
   sweep". At 1 Hz frames and millisecond reply latency these are the same
   value; when they differ the later one is more accurate. Immaterial — worth a
   one-word design edit if §3.4 is ever revisited.

## Residual risk for the user's first flight with this on

Everything below is sim-only and cannot be checked on this machine; T-006's own
risks list flags the same set, and I confirmed none of it is reachable here.

- **A duplicate "you" marker** sitting on the user's own aircraft, if MSFS
  reports a different object id for the user in an `AIRCRAFT` sweep than for
  `OBJECT_USER`. Guard 2 (0.0001° box) should catch it. Watch for a small amber
  or grey `✈` glued under the big own-aircraft one.
- **An empty or never-clearing traffic layer.** If an empty sky delivers *no*
  event instead of one `outOf === 0` event, the last snapshot simply ages out
  after 10 s and the map clears — self-healing. If markers instead freeze in
  place, the sweep tail is being lost.
- **Wrong altitudes or all-grey traffic**, if `PLANE ALTITUDE` /
  `GROUND VELOCITY` / `SIM ON GROUND` behave differently for AI objects than for
  the user aircraft.
- **The agent exiting mid-flight** (follow-up 1). The symptom is flight logging
  stopping, not just traffic disappearing — if that happens, use the opt-out and
  report it.

**How to turn it off**, quoted from `agent/README.md`:

> Set `TRAFFIC_ENABLED=0` to turn gathering off entirely — no data definition is
> registered, no SimConnect request is made, and nothing is posted.

and from `README.md` for the server side:

> Set to `0`, `false`, `off` or `no` to make `/api/ingest/traffic` discard every
> batch it receives (`204`, no validation, nothing stored).

Setting it on the agent alone is enough and is the cheaper of the two; the
server-side switch is independent and needs a server restart to take effect.
Nothing else needs undoing — no schema, no data, no dependency was added.
