## Findings (all non-blocking)

**F1 — the live checkout was built while this task was in flight.** `dist/index.js` (20:16:14) and
`client/dist/{index.html,assets/*}` (20:16:10) are newer than the implementer's source edits
(`src/auth/ingestScope.ts` 20:15:02, `tests/ingestScope.test.ts` 20:15:35) and older than this
review session. `grep -rl ground-section-toggle client/dist/assets/` matches
`index-BI1xHYYp.css` — a class that exists **only in the uncommitted `client/src/index.css` diff**.
`src/server.ts` serves `client/dist` from disk on every request, so the user's running server is
right now serving an uncommitted UI (the unrelated ground-session Home.tsx/CSS work in the tree),
and `dist/auth/ingestScope.js` already contains the two new entries, so the user's next restart
ships this change whether or not it was approved. This is the exact hazard
`ENVIRONMENT.md` § "Verifying a client-side change without touching the live server's client/dist"
and the `feedback_env_var_pipe_scoping` memory warn about. Attribution is inferred from mtimes, not
proven. Remediation (rebuild `client/dist` from a committed state, or leave it) is an
Orchestrator/user call, not a code fix — hence non-blocking, but it should not be silent.

**F2 — the token now reads an account setting.** `GET /api/settings/simbrief` returns the SimBrief
Pilot ID. The prior run's frozen decision described the token's blast radius as "nothing
session-only (flight history browsing, account settings, etc.)". This run's goal explicitly asks for
this route, so it is authorized, not a violation — but the earlier characterisation is now stale and
worth a line in `intake.md`/README so the next reader does not rely on it.

**F3 — unrate-limited write + outbound fetch behind the token.** `POST /api/planned-legs/simbrief`
creates a `planned_legs` row, files an ACARS dispatch message, and makes a real call to
simbrief.com. A leaked token can repeat it without bound (`allow_duplicates:true` bypasses the
dedup). Pre-existing handler behaviour; the token simply now reaches it. Follow-up, not a blocker.

**F4 — malformed JSON on this route returns an HTML stack trace.** `-d '{"broken":'` →
`400` with a 1023-byte HTML page exposing `/home/guilherme/msfslogger/node_modules/...` paths.
Identical for a session cookie (verified), so it is pre-existing, not a regression — the app error
handler only maps `INVALID_BODY` for `req.path.startsWith('/api/settings/')`. Now reachable by a
cookie-less client. Follow-up: widen that branch.

**F5 (advisory, half-verified)** — `POST /api/planned-legs/simbrief/` with a trailing slash gets
`401` for a token client (verified), because the allowlist is path-exact by design, while express's
non-strict routing would still dispatch the handler. I did not verify the session half. The MCDU
sidecar must use the exact path; worth one line in the sidecar hand-off JSON.
